# Adapter behavior invariants

本文记录 Eagler Touhou 现有适配中已经确认、但仅阅读原作代码或基础
Adapter 协议通常无法自然推导出的成品行为要求。

这些要求主要来自两类情况：

- 为触控、浏览器、高刷新率或新渲染后端主动补充 / 改写原作交互，
  以保持成品体验；
- 即使存在多种技术上都“实现正确”的方案，Eagler Touhou 仍必须明确
  选择其中一种用户可观察语义。

本文描述的是**最终应该怎样表现**，而不是规定唯一实现方式。“参考实现”
用于说明已经验证过的实现方向；等价实现只要保持同样的行为语义即可。

纯实现错误、缓存 / 状态管理 / 时序陷阱、renderer 内部修复方法不属于本文，
应记录在维护者 Playbook 中。一个问题如果只有在实现写错时才会发生，而不存在
另一种同样合理的产品语义，就不应进入本文。Launcher 已统一拥有的布局编辑、
放大镜、Package、共享启动流程和公共 UI 也不在每作重复规定；新的 Runtime 应
直接复用共享实现。

除非本文明确覆盖某个行为，原作本身的 gameplay / menu 语义仍是默认基线。

## Gamepad

### 手柄键位必须跨设备保持同一逻辑语义

**目的：同一份游戏内 KeyConfig 在 DS / Xbox / Steam Controller 等受支持手柄上必须表示同一组逻辑按钮，不能因为操作系统、浏览器或驱动暴露的 raw button index 不同而改变。**

KeyConfig 读取到的按钮编号与 Gameplay 实际消费的按钮编号必须来自同一个标准化手柄语义。玩家在 KeyConfig 中重新绑定 Slow / Shot / Bomb / Pause 等动作后，进入游戏必须立即按该绑定工作；不能出现配置菜单完全收不到手柄、配置显示已改变但 Gameplay 仍读另一套编号、或换一种手柄后同一编号变成另一颗物理键。

默认绑定本身也必须在常见标准手柄上提供可用的 Shoot / Bomb / Focus / Pause 等核心操作；KeyConfig 是自定义入口，不应成为“先修好默认手柄支持才能玩”的必经步骤。

方向键同样不能依赖某个驱动恰好把 D-pad 暴露成固定 raw buttons；D-pad 应进入稳定的方向语义。

**参考实现：** TH06 / TH07 已通过 SDL Gamepad 标准化物理控制器。TH08 / TH10 也应在平台输入边界先使用 `SDL_Gamepad` 将 South / East / West / North、肩键、Start / Back / Stick 等转换为稳定的原作 KeyConfig 逻辑槽位，再交给各作自己的输入状态机；不要把 `SDL_Joystick` 的设备原始按钮序号直接持久化或当作游戏键位。

### 手机外接键盘不能只依赖 KeyboardEvent

**目的：Android / Chromium 等环境下的蓝牙或 USB 键盘、遥控器、复合输入设备必须仍能稳定控制游戏方向。**

浏览器可能把某些设备的 D-pad 同时或仅作为 Gamepad API 输入暴露，并吞掉原本期望的 DOM KeyboardEvent。适配不能因此让方向键在手机上完全失效，也不能为了兜底而把真实游戏手柄的按钮重复解释成键盘输入。

**参考实现：** 普通键盘继续走共享 Launcher 的 hosted keyboard bridge；Runtime 解析 hosted keyboard 消息时不能只信 `event.code`，还要在 `code` 为空或 `Unidentified` 时使用 `key` / legacy `keyCode` 恢复同一逻辑键，并正确处理 modifier / Numpad location。另只对 Gamepad API 中设备 ID 明确呈现 keyboard / kb 语义的设备读取标准 D-pad 12–15，并转换为普通 Up / Down / Left / Right。真实手柄仍由 SDL Gamepad owner 处理。TH06 / TH07 已有这两类兜底，后续作品必须继承同一行为。

## Touch

### 全显示区域触控

**目的：触控不应受 4:3 游戏画面边界限制。**

手机横屏时，游戏画面外的黑边也应能开始操作；手指在游戏画面与黑边之间移动时，当前操作不应中断。

**参考实现：** 浏览器层监听整个游戏显示区域的触摸；画面外触摸也转换为游戏触摸事件，并使用同一 pointer / finger ID 持续转发 down / move / up。

### 多指操作彼此独立

**目的：增加或抬起辅助触点时，不应无故打断仍在进行的移动或其他触控操作。**

例如移动中的手指不应因为另一根用于低速、Bomb 或其他操作的手指抬起而失效。

**参考实现：** 分别维护各触点当前承担的职责，只结束实际抬起或失效的那个触点所拥有的操作。

### 菜单一次滑动只进行一步

**目的：菜单触控应保持离散、可预测。**

一次 swipe 无论滑动多远，只进行一次 Up / Down / Left / Right；抬手后才能开始下一次菜单移动。单指短 tap 用于确认，双指短 tap 用于返回。

**参考实现：** 一个完整 down → move → up 生命周期作为一次菜单 gesture，由原游戏普通方向 / Confirm / Cancel 输入完成菜单操作。

### 对话短按与长按行为明确分离

**目的：对话触控既能精确推进，也能方便连续 Skip。**

短 tap 只推进一次；持续按住才进入连续 Skip，两种 gesture 不应互相误判。

**参考实现：** 记录触点按下时间和移动距离，短时间且位移较小时产生一次 Confirm，达到长按时间后持续输出 Skip。

### 不可操作对话保持 Gameplay

**目的：自动播放、不可由玩家推进的对话不应夺走 Gameplay 的触控控制。**

这类对话出现时，玩家仍应可以继续移动；触摸不能被解释成菜单方向、Confirm 或 Cancel。

**参考实现：** 只有对话当前可 Skip 或正在等待玩家推进时，才切换到 dialogue touch；否则继续按 gameplay touch 处理。

细节：**“仍处于 gameplay”主要指移动等 gameplay ownership 不被夺走，不代表一定允许射击。** 原作本身如果在对话期间禁止 Shoot，就继续服从原作。

### 抬手后立即停止残留移动

**目的：松开移动手指后，角色不能继续“追赶”之前尚未消费完的拖动距离。**

尤其是有限速 Direct Touch 下，即使之前快速拖了很远，抬手也代表这次移动操作已经结束。

**参考实现：** 移动触点结束时同时释放 movement owner，并清掉尚未消费的移动 delta / drag target。

### Bomb 手势不能抢走移动

**目的：使用触控 Bomb 时，不应要求玩家先停止移动。**

例如双击 Bomb 可以由另一根手指完成，当前负责移动的手指继续保持控制；触发 Bomb 本身不能取消移动 gesture。

**参考实现：** Bomb tap/double-tap 单独维护 gesture 状态，不取得 movement ownership，也不清理当前 movement finger。

### 限速触控不能丢掉快速拖动的距离

**目的：限速应限制角色移动速度，而不是丢弃用户已经拖出的距离。**

手指快速拉远后，只要仍然按着，角色应继续追向该目标；不能因为单帧超过最大速度就把剩余位移扔掉。

**参考实现：** 保留尚未消费的 touch delta / target，每个逻辑帧只消费角色当前速度能够完成的部分。

### 触控几何不应随窗口大小改变手感

**目的：同一个灵敏度和同一个手势，在窗口、全屏和不同手机分辨率下应该有接近一致的含义。**

不能因为屏幕变大，就让 100% 灵敏度突然变慢，也不能让 swipe / tap 判定阈值发生明显变化。

**参考实现：** 先把触摸位移和 gesture threshold 换算到游戏逻辑画布尺度，再进行灵敏度、swipe、double-tap 等判定。

### 手势时间使用真实经过时间

**目的：掉帧、高刷或游戏逻辑速度变化不能改变长按、双击等手势的手感。**

例如“按住约 500 ms 才 Skip”不应该因为游戏卡顿而变成实际一秒多。

**参考实现：** double-tap、long-press 等时间窗口使用单调的真实时间计时，再把识别结果转换成游戏逻辑输入。

### 浏览器自己的触摸行为不能和游戏抢手势

**目的：长按菜单、页面滚动、浏览器缩放、文本选择等行为不能在游戏过程中抢走 Touch。**

**参考实现：** 游戏区域使用 touch-action: none，并在游戏拥有的 pointer gesture 上阻止浏览器默认行为；共享 Launcher 也会拦截 player 区域的 contextmenu / selection / drag / browser gesture。

### 流程等待确认必须可触控推进

**目的：玩家不能因为只使用触控，而卡在原作需要 Confirm / Z 才能继续的流程画面。**

例如 Stage Clear、Bonus、Practice 单关结束后的等待确认画面，也必须能够通过触摸继续。

**参考实现：** 当当前游戏流程实际等待原作 Confirm / Z 输入时，触摸短按产生同一普通 Confirm 输入；不要只根据“是否是可跳过 Dialogue”判断 Touch owner。

### Bomb 必须服从原作 Bomb / Deathbomb 判定

**目的：同一次 Bomb 操作不能因为输入来自触摸而失去原作允许的决死时机。**

玩家在原作允许 deathbomb 的窗口内触发触控 Bomb，应与键盘 Bomb 得到相同结果；反过来，已经错过窗口的 Bomb 也不能因为触控实现而延迟到复活后执行。

**参考实现：** Touch 只负责在当前逻辑帧提交普通 Bomb 输入，是否接受由原作 Player / Bomb 状态机决定；移动暂时不可用不能顺带屏蔽 Bomb。

### Unlimited Touch 作弊移动必须改变处理落率

**目的：使用突破原作移动限制的 Unlimited Touch 后，本局不能继续被当作普通原版输入成绩处理。**

**参考实现：** 只有 Unlimited Touch 实际产生过不限速移动后，才将本局标记为使用了作弊移动，并让 Result / Replay 中原本用于反映处理落ち的数值按项目既定语义强制为 100%。仅开启 Unlimited Touch 但没有实际使用，不应污染本局。

### 触控灵敏度不能改变角色原版速度

**目的：调高触控灵敏度应减少手指需要拖动的物理距离，而不是让角色突破原版高速 / 低速移动速度。**

**参考实现：** 灵敏度作为“手指位移 → 目标位移”的线性倍率；角色仍按原作每逻辑帧允许的速度追向目标。

## Touch Replay

### 触控 Replay 显示触点

**目的：** 播放包含触控输入的 Replay 时，应显示录制时的实时触摸位置，便于观察玩家的触控操作。

**参考实现：** TH06 / TH07 在每个仍按住的 Replay 触点位置绘制一个小型白色 +；多指同时显示多个，触点结束后消失。后续作品应沿用这一视觉语义。

## Audio

### 前后台切换后音频必须真正恢复

**目的：切到后台再回来后，不能出现静音、卡音或音频永久停止。**

恢复时只恢复浏览器输出能力，不能因此重新开始 BGM、改变游戏原本的 Pause / Fade / 曲目状态。

**参考实现：** 前台恢复时先恢复浏览器 AudioContext，确认输出层可用后再恢复 SDL / Runtime 音频；若浏览器要求用户手势，则在下一次真实输入时继续恢复。

### 切曲必须覆盖完整的 source switch 生命周期

**目的：连续切歌时不能短暂重复上一首、卡住旧声音或出现新旧音频交叠。**

**参考实现：** 在旧音源停止、新 OGG 打开/读取/解码、新音源建立的整个切换期间暂停浏览器输出，完成后再恢复。不同作品内部做法可以不同，但不能只保护切换过程中的一小段。

## Browser lifecycle

### Web 失焦不等于进入后台

**目的：iframe / canvas 暂时失去 DOM focus 时，游戏不能因此冻结。**

移动浏览器里一次触摸结束、HUD 操作或焦点转移都可能产生 blur / focus lost，但页面实际仍在前台。

**参考实现：** Web 下遇到 window focus lost 只清理临时触控状态；真正暂停 Runtime / Audio 由 visibilitychange / pagehide / background 生命周期负责。

## Localization

### 原版字体与翻译字体必须严格隔离

**目的：选择原版日文时，游戏正文必须保持原作的日文字体语义；启用翻译时，才切换到能够覆盖翻译字符的 Unicode 字体。**

仅仅因为 Runtime 同时加载了 Unifont，或者因为启用了 thprac，不能让原版日文正文也改用翻译字体。反过来，thcrap 翻译文本也不能继续依赖原版日文字体，导致缺字、错误 fallback 或字形异常。

**参考实现：** 当前 TH06 / TH07 Web 在 Localization 未启用时正文使用 msgothic.ttc；Localization 启用后正文使用 unifont.otf。共享资源可以同时存在，但实际使用哪套字体由当前文本 owner 决定。

## THPrac

### thprac 语言跟随产品语言，但拥有独立的语言状态

**目的：thprac 菜单应使用玩家当前选择的产品语言，不能固定成英语、系统语言，也不能错误依赖游戏正文的 thcrap 激活状态。**

例如简中游戏对应简中 thprac，日文原版对应日文 thprac，英文翻译对应英文 thprac。即使日文模式没有加载 thcrap 翻译包，thprac 仍应正常显示日文。

**参考实现：** Launcher 将当前产品语言显式映射为 thprac 自己的 locale；thprac 使用独立 locale table 渲染 UI，而不是从 Localization::Active 推导自己的语言。

### thprac 字体必须覆盖当前语言的实际 UI 字符集

**目的：选择一种 thprac 语言后，所有实际会显示的标签、章节名和选项都必须有真实字形，不能出现 ?、方框或缺字。**

语言改变也不能只替换字符串；不同语言文字长度明显不同时，菜单布局仍应保持可读，避免截断、重叠或控件宽度明显不足。

**参考实现：** Web thprac 使用 unifont.otf，并按当前 locale 构建足够的 glyph coverage；简中不能只依赖常用字符子集，日文也要覆盖实际使用的日文字形。必要时窗口尺寸和位置随 locale 调整。

## High refresh

### 高刷覆盖验证【待完善】

**目的：** 在保持 60Hz 游戏逻辑不变的前提下，尽可能让所有适合高刷新呈现的视觉运动得到高刷表现。

**现状：** 当前主要依赖插值与人工观察来发现遗漏，但这种验证方式不够可靠；人眼难以稳定判断某个对象是否仍按 60Hz 更新，也缺少成熟的自动化覆盖检测方法。

**待完善：** 后续如果出现更可靠的高刷覆盖分析、渲染采样或自动检测方法，应优先替换现在依赖人工观察的验证方式。

## Rendering

### 最终绘制阶段不能吃掉亚像素运动

**目的：高刷 / 插值得到的连续亚像素运动，不能在最终 sprite / geometry 绘制阶段又被整数像素吸附重新量化。**

否则前面的 presentation 已经正确生成小数位置，最终画面仍会退化成按整像素跳动，看起来像高刷插值没有生效。

**参考实现：** 最终提交顶点时保留 fractional presentation coordinates；不要对普通连续运动统一 round / floor 到整数像素。只有确实需要 pixel-aligned 语义的视觉元素才继续进行像素吸附。

### 附着视觉必须跟随主体的最终呈现

**目的：主体已经平滑呈现时，依附于它的视觉元素不能仍以另一套节奏移动、抖动或与主体分离。**

例如 Option、判定点、名字、提示、附着特效，以及由主体位置派生的文字或装饰，都应与主体保持一致的最终画面关系。

**参考实现：** 先得到主体当前的最终呈现位置，再从这个结果派生 attached visuals；也可以使用其他等价方式，只要不要让依附对象建立一套与主体脱节的独立运动语义。
